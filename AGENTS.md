# Working agreement

Brander develops brands, products, prototypes and production material. This repository owns the complete [studio requirements](STUDIO.md), brand decisions, production sources, authoritative assets, tools and local methods below. The selected central project home owns registration, routing and workspace continuity; its location is supplied by the task/session.

## How work proceeds

Identify the outcome, selected brand/production, authorized writes, requested deliverables and stop. Read the studio entry and only affected owners. Inspect applicable source and nested instructions before editing. Research, review and planning do not authorize implementation; saving a plan authorizes only its record. Resolve material unknowns before dependent work, then implement, verify and deliver within scope.

For base-led work, use the selected base's shared methods with these repository-owned studio requirements. For independent work, use the local routes below. Neither entry creates a second task record or editable baseline. Links do not establish host loading or precedence; follow actual host priority and explicit user direction.

### Proportional handling

Handle one clear correction directly. For work needing continuity, select one explicit task and maintain its single record under [production records](PRODUCTION.md#revisions-and-records). Supporting documents need substantial content or a requested artifact. Continue routine professional choices within the brief. Ask only when an unresolved choice materially changes purpose, identity, commitments, cost or acceptance; honor explicit review stops.

## Workspace handling

[PRODUCTION](PRODUCTION.md#revisions-and-records) owns the shared task layout, one editable baseline, meaningful version retention and requested exports. [COMMERCIAL](COMMERCIAL.md) adds film requirements. Existing layouts remain in place when sufficient; never infer a current target from the newest file.

## Authority and scope

Preserve unrelated changes, supplied originals, approved direction, existing productions, histories and user-managed processes. Source selection gives location, not write permission. Product applications and deployment remain in dedicated repositories; select their owners and obtain scope before changing them. Do not stage, commit, push, publish, deploy, change provider/access configuration or install dependencies unless authorized. Manage only task-created resources; check ownership and health before reusing a service. Identify cleanup candidates separately; do not delete or relocate existing material without scope.

## Tools and reporting

Use available tools against the selected deliverable; package defaults cannot change the brief, directories, retention or authorization. Establish runtime and provider prerequisites when needed. Missing required capability blocks dependent work; never invent a successful render, generation or check. Report changes, actual checks, failures, remaining requirements and next action in the user's language. Keep observed results, technical verification, delivery and user approval distinct. Instruction source and maintained documentation use English.
